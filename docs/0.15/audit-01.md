## Findings, highest severity first

### 1. High — a completed midnight-ending legacy task makes the week save fail

**Branch:** `grok/0-15-full-day` at `d4bfd92`. **Evidence:** `backend/assignments.py:26-36` formats the end of a 23:45–24:00 block as `YYYY-MM-DDT24:00`; `backend/models.py:47-52,265-270` accepts timestamps only through `23:59`; `backend/app.py:130-154,1303-1308` validates that generated assignment during a legacy week save. With an authenticated test client, a completed flexible block at Monday 23:45 for 15 minutes returned HTTP 500 from `PUT /api/week`; a subsequent `GET /api/week` still returned revision 0 and no blocks. This is an unrecorded boundary defect introduced by the full-day range, not a requested policy change. **Recommendation: fix in code.** Normalize a midnight completion to the following date at `00:00` before assignment validation; add an API regression test for a completed legacy block and Pomodoro work session ending at 24:00.

### 2. Medium — the source gate is red at a point the plan says each unit ends green

**Branches:** both Grok branches. **Evidence:** `docs/0.15/plan.md:69-86` says each unit ends green on the source gate, while Unit 5 explicitly defers 15 stale tests. On `dc9b7fa`, `.venv/bin/python scripts/verify.py` failed those 15 tests (1,136 passed). On `d4bfd92` it failed 16 (1,148 passed): the same 15 retired-widget references, such as `desktop/tests/test_layout_drag.py:324` and `desktop/tests/test_layouts_window.py:302,1055`, plus `desktop/tests/test_native.py:794-817`. The latter expects homework to remain unplaced after Monday 06:00–23:00 fills, but the new full-day default correctly finds 00:00. Thus the full-day branch introduced one new stale expectation while both branches violate the plan's per-unit green gate. **Recommendation: fix in code.** Migrate the 15 retired-widget tests to observable new-surface behavior and update this old-hours fixture to set explicit work windows or assert the intended new behavior before treating either unit as gate-green.

### 3. Medium — date-only due work sorts ahead of earlier timed deadlines

**Branch:** `grok/0-15-optional-due` at `dc9b7fa`. **Evidence:** the new parser correctly assigns date-only due an end-of-day bound (`backend/models.py:55-67`), but Day sorts by raw `due` text (`backend/day.py:56-69`), as do Month and the assignment list (`backend/month.py:110-112`, `backend/app.py:1323`). For a Tuesday `09:00` task and an untimed Tuesday task, `_due_soon` returned the untimed task first. The same lexical key occurs in `desktop/native/weekmodel.py:252` and `desktop/native/calendar.py:346`. An urgent morning deadline can therefore appear below an all-day one. **Recommendation: fix in code.** Sort through the shared parsed `(date, minute)` deadline, with ID as a tie-breaker, in each due-ordered list; add a mixed date-only/timed ordering test.

### 4. Medium — the optional-due last-slot test can pass for the wrong refusal

**Branch:** `grok/0-15-optional-due` at `dc9b7fa`. **Evidence:** `desktop/tests/test_calendar.py:188-197` says only that the 23:00–23:45 placement is *not* an after-due refusal, and guards the required success assertion behind `end_of_day <= DAY_END_MIN`. On this branch `DAY_END_MIN` is still 23:00 (`backend/slots.py:5-8`), so that guard is false and `span_problem` returns the old outside-hours refusal. The brief explicitly requires proving that a 23:45 finish on the due date is allowed (`docs/0.15/handoffs/grok-optional-due-time.md:39-45`). This is a false-green test; the two parallel branches need integration before that acceptance case can run. **Recommendation: fix in code.** After merging the full-day range, assert `span_problem(...) is None` for the actual 23:45 ending, with no conditional, and keep the timed 09:15 refusal assertion.

### 5. Medium — Classic Day rig navigation can pass without the Day tab working

**Branch:** `feat/0.15-tabs` at `248a318`. **Evidence:** all four Day scenarios enter the view through `session.open_day(thursday_iso)` rather than a pointer action (`scripts/rig/drive.py:339-342`). The separate Week open-day scenario only asserts `session.planner_view` and `session.selected_day`, not that a Day surface is visible (`scripts/rig/drive.py:454-463`). A broken Day tab can leave these 12 pointer scenarios green because the Day fixture bypasses that control. **Recommendation: fix in code.** Navigate through the visible Day control in the Day fixture and assert the intended Day canvas is visible after each navigation path.

### 6. Low — the rig still rewards the retired full-week fit rule

**Branch:** `feat/0.15-tabs` at `248a318`. **Evidence:** `scripts/rig/drive.py:465-471,511` passes when only 06:00 and 23:00 fit the planner rectangle. `docs/0.15/plan.md:20-24` instead requires scrolling and zoom over 00:00–24:00, with no full-day fit requirement. This check can report green while midnight is unreachable and can later reject the intended scrollable Week. **Recommendation: fix in code.** Replace it with top/bottom reach and zoom-level checks when the Unit 3 surface lands; do not count `week-fits` toward the 0.15 release matrix.

## Verification and interpretation

- At `248a318`, the local real-pointer rig passed Classic Day 4/4 and Week 8/8. The Week pass includes the obsolete `week-fits` scenario and does not establish the larger matrix.
- Focused full-day tests passed 88 cases; focused optional-due tests passed 55 cases; base geometry/hand tests passed 17 cases. The full-day source gate failed 16 tests (15 inherited stale-widget references and one new old-hours expectation), with 1,148 passes. The optional-due gate failed the 15 inherited stale-widget references, with 1,136 passes. Both had no skips; lint and backend types passed. GLM provided a first-pass contract check; its suggestions were checked against the controlling plan and code before inclusion.
- On the same local input (five school days at 08:00–14:30, a daily 22:00–23:00 lock, and twelve 45-minute flexible tasks due Sunday 21:00), 20 sequential `solve` calls had a median reported time of 2.18 ms at `248a318` versus 7.12 ms at `d4bfd92`; maxima were 5.83 and 10.77 ms. Both completed all tasks within the 150 ms budget. This is one fixture on this machine, not the missing implementation-branch timing report or a worst-case guarantee.
- Clamping outside the track is an approved decision. The currently missing *track-local* limits would break a partial-day tile if a design migrated today; that gap is already recorded as Unit 7, so it is not relabeled as an unrecorded finding. For example, an 18:00–21:00 tile could currently yield a 22:00–23:00 move instead of clamping to its own end. Likewise, the missing target protocol, press-time render hold, date-aware Month judge, and old `QDrag` designs are explicit future units. The latest full-day fix is real for touching windows, refusal reason/copy, and the globally unset default; it does not mean every uncovered weekday stays open after preferences are set. `spec.md` drift is known release work under Unit 17 and requires Jonathan's approval before amendment.
